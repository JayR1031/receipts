# ADR-0008: Optional Google sign-in, per-user History and daily run limits

**Status:** accepted · **Date:** 2026-11-15 · GitHub issue #41. The repository owner (`JayR1031`) decided on 2026-11-15, answering the brief's first question for issue #41, that sign-in is optional (option b): a signed-in visitor starts runs without the passcode under a per-user daily limit, and a signed-out visitor keeps the passcode path under a global daily cap on signed-out runs.

## Context

Issue #41 asks for "Sign in with Google", History that shows only the visitor's own runs, and a per-user daily run limit. The owner plans to post the app publicly, and hackathon judges may open it while the Google OAuth app is still in Testing mode, when only the owner can sign in. Mandatory sign-in would stop judges and visitors from starting any run. Keeping only the passcode, with nothing counting signed-out runs, would let anyone who sees a leaked passcode spend the Anthropic and Keenable budget, which the spec names as an anti-goal. Option (b) keeps both paths and counts each.

Sign-in needed three things the code did not have:

- an OAuth 2.0 authorization-code flow against Google with PKCE (Proof Key for Code Exchange: the browser never holds a reusable secret, because the code is bound to a one-time verifier the server keeps);
- verification of Google's ID token, a JSON Web Token signed with RS256 (RSA) whose public keys Google publishes as a JSON Web Key Set (JWKS);
- a signed session cookie that carries our user id and an expiry.

Python's standard library can compute an HMAC (enough for an HS256 cookie) but cannot verify an RSA signature, and before this change no JOSE or cryptography package was in the lock (`uv.lock` at `6e59412` has no `pyjwt`, `joserfc`, `python-jose`, `cryptography` or `itsdangerous` entry).

`pyproject.toml`, `uv.lock` and `src/receipts/settings.py` have been frozen since Wave 0 (AGENTS.md section 9, ADR-0006). The freeze matters because every lane builds against the same locked environment and the same lazy `Settings`, and `settings.py` is what lets the image boot with no secrets (ADR-0005; `tests/test_settings.py::test_create_app_boots_with_an_empty_environment` and CI's api-image boot both start the app with an empty environment). Changing any of the three needs the owner's approval on record.

## Decision

- **The freeze is lifted for issue #41 only**, on exactly three files: `pyproject.toml`, `uv.lock` and `src/receipts/settings.py`. `src/receipts/contracts.py`, `src/receipts/fakes/**` and `tests/conftest.py` stay frozen: `RunService.start(request)`, `RunRepo.list_runs()` and `RunSummary` do not change. Nothing else in the freeze changes.
- **One runtime dependency: `joserfc>=1.8.0`** (1.8.0 locked; PyPI upload 2026-11-03, the lock's `upload-time`), added with `uv add joserfc`. The lower bound is the version uv picked, as for the other dependencies; no exact pin, because nothing here relies on one release's internals. joserfc is a JOSE library: HS256 sign and verify for our session and OAuth round-trip cookies, and RS256 verification of Google's ID token against Google's published key set (`joserfc.jwk.KeySet.import_key_set`). It requires `cryptography>=45.0.1`, and the lock adds exactly joserfc 1.8.0, cryptography 50.0.2, cffi 2.1.1 and pycparser 3.12 (`uv tree --package joserfc --no-dev`). The brief's default was a larger OAuth library, `authlib` (the second entry under Alternatives considered). joserfc replaced it on 2026-11-16, on the orchestrator's ruling, for three reasons:
  - **The default is untyped; joserfc is typed.** The default ships no type information, and pyright checks `src/receipts/auth/` in strict mode with `# type: ignore` forbidden (ADR-0006), so its functions come through as partially unknown types, which strict mode reports as errors (measured under Alternatives considered). joserfc ships `py.typed` (`joserfc/py.typed` in the installed 1.8.0).
  - **The default's own JOSE module is deprecated.** Importing it prints a warning that tells users to switch to joserfc.
  - **joserfc is what the default uses itself.** The default declares `joserfc>=1.6.8` as a requirement, and the two packages have the same author and licence (BSD-3-Clause). Depending on joserfc directly keeps the JOSE code and drops the untyped, deprecated layer on top of it.
- **The OAuth 2.0 client side uses the standard library and `httpx`; no OAuth package.** PKCE uses the standard library: the verifier comes from `secrets`, and the S256 challenge is the base64url SHA-256 of the verifier, without padding (`hashlib`, `base64`). The authorization URL is built with `urllib.parse`. The token exchange and the fetch of Google's key set use `httpx` 0.28.1, which is in the lock but **not declared** as a runtime dependency: `pyproject.toml` lists it only in the dev group. It reaches the runtime image through 8 locked runtime packages (`uv tree --frozen --invert --package httpx --depth 1 --no-dev`: gradio, gradio-client, huggingface-hub, langchain-core, langgraph-sdk, litellm, ollama, safehttpx), and `src/receipts/auth/provider.py` is the only module in `src/` that imports it. The orchestrator ruled on 2026-11-16 to leave it undeclared, because the brief allows exactly one added runtime dependency and declaring `httpx` would add no package. The risk: if all 8 of those packages dropped `httpx`, the app would fail at import (`receipts.api.app` imports `receipts.auth.routes`, which imports `receipts.auth.provider`), and CI's api-image boot would fail before a deploy. The owner may declare it in a later PR. joserfc adds no path to `requests`: `uv tree --invert --package requests --depth 1 --no-dev` lists the same five direct users before and after this change (langchain-keenable, langsmith, mellea, requests-toolbelt, tiktoken).
- **Five settings, all optional**, on the existing lazy `Settings` in `src/receipts/settings.py`. They are read per request through `get_settings()`, never at import and never in `create_app()`. Because every field is optional, reading them in an empty environment would not fail, so `tests/test_settings.py::test_create_app_boots_with_an_empty_environment` also asserts that import and `create_app()` leave `get_settings`'s cache empty. That proves neither calls `get_settings()`; it would not catch a direct `Settings()` call, and the only one in `src/` is inside `get_settings` (`grep -rnE "\bSettings\(" src/`).

  | Variable | Field | Default |
  |---|---|---|
  | `GOOGLE_CLIENT_ID` | `google_client_id: str \| None` | `None` |
  | `GOOGLE_CLIENT_SECRET` | `google_client_secret: SecretStr \| None` | `None` |
  | `SESSION_SECRET` | `session_secret: SecretStr \| None` | `None` |
  | `RUNS_PER_USER_PER_DAY` | `runs_per_user_per_day: int` | `5` |
  | `SIGNED_OUT_RUNS_PER_DAY` | `signed_out_runs_per_day: int` | `20` |

  The client id is a plain `str` because it is not a secret: it appears in the authorization URL every visitor's browser sees. The module docstring's list of names grows from five to ten. Sign-in needs `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `SESSION_SECRET` and `DATABASE_URL`; with any of them missing (unset or blank), `/auth/login` and `/auth/callback` answer 503 naming the first missing one, never a value, the UI shows no sign-in link, and everything else works as before.
- **Shared types and one seam for the UI.** `src/receipts/auth/models.py` holds the frozen domain types (`User`, `SessionUser`, `IdTokenClaims`, `StartDecision`, `AccountStatus`, `AuthError`). One more shared type lives in `src/receipts/auth/oidc.py`, not `models.py`: `OAuthRoundTrip` (state, nonce and PKCE verifier of one sign-in attempt), used by `oidc`, `session` and `routes`. `src/receipts/auth/provider.py` holds the `IdentityProvider` protocol and the real class, `GoogleIdentityProvider`. `src/receipts/auth/fake.py` holds `FakeIdentityProvider`, chosen only by explicit injection, never by an environment variable. `src/receipts/auth/gate.py` holds the `Gate` protocol, the only way identity reaches `src/receipts/ui/`. `create_app()` stores the live `Gate` (`LiveGate`, `src/receipts/api/wiring.py`) on `app.state.gate` before `mount_ui(app)`; with no `Gate` there, the UI behaves as it did before this ADR.
- **Sign-in, as shipped** (`src/receipts/auth/routes.py`, all on the app's own domain, ADR-0005):
  - `GET /auth/login` makes a fresh state, nonce and PKCE verifier, puts them in a signed round-trip cookie (`receipts_oauth`, 10 minutes) and answers 302 to Google's authorization endpoint for the scopes `openid email` only. A request on `127.0.0.1` is first sent (302) to `http://localhost:8000/auth/login`: the cookies are host-only and the registered local callback is on `localhost`.
  - `GET /auth/callback` checks, in order: the round-trip cookie verifies; `state` equals the cookie's (constant time; present is not enough); the provider swaps the code for the ID token's signature-verified claims; `validate_claims` checks issuer, audience, expiry and nonce. Only then is the `users` row read or created and the session cookie set; the browser goes (302) to `/ui`. A failed check is 400 `sign-in check failed: <check>`, names the check only, writes no row and sets no session cookie. Any database error from the users store (building it, its schema, or the row; any `SQLAlchemyError`) is 503 `sign-in check failed: user_store`, and the error is dropped unread, because its text carries the bound `sub` and email. Every failure after the round-trip cookie verified also clears that cookie.
  - `POST /auth/logout` clears the session cookie and answers 303 See Other to `/ui`. `GET /auth/me` is 200 `{"email": ...}` (`Cache-Control: no-store`) for a valid session whose `users` row exists, else 401.
  - Both cookies are compact JWTs signed with HS256 under `SESSION_SECRET` (joserfc, algorithm pinned), flagged `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`. The session cookie (`receipts_session`, 7 days) carries `{uid, exp}` only: our internal user id and its expiry, never the email or a Google token. Signed, not encrypted: the browser that holds a cookie can read it, which is why each carries only these values. The two lifetimes are constants in `src/receipts/auth/session.py`, not settings.
- **The ID token's signature is verified against Google's published keys.** `GoogleIdentityProvider.exchange` POSTs the code, the redirect URI, the PKCE verifier and the client id and secret to `https://oauth2.googleapis.com/token` (10 second timeout), keeps only `id_token` from the reply (the access token is dropped at parse, never stored), reads the token's `kid` (required, non-empty), fetches Google's key set from `https://www.googleapis.com/oauth2/v3/certs` unless the cache holds that `kid`, and verifies the RS256 signature with joserfc, the algorithm pinned to RS256 and the key set reduced to RSA keys. Only the verified token's claims leave the provider, and the route then passes them to `validate_claims` (`src/receipts/auth/oidc.py`): issuer `https://accounts.google.com` or `accounts.google.com`, audience equal to our client id, `exp` after now, nonce equal to this attempt's. The signature check is not skipped because the token arrived over TLS. Every provider failure is an `AuthError` naming `token_exchange`, `jwks` or `id_token`.
- **The identity provider is built once per process.** `receipts.auth.routes.get_identity_provider` builds the real `GoogleIdentityProvider` on the first callback that needs it (after the 503 availability check) and caches it on `app.state.identity_provider`; nothing builds it at import or in `create_app()`. Its key cache has no expiry and does not read `Cache-Control`: it fetches Google's key set again only when a token names a `kid` the cache does not hold, and the new set replaces the old. So a key Google has withdrawn stays trusted in this process until a token with an unknown `kid` forces a refetch, or the process restarts. Why: a provider per request would cost one more GET to Google for every sign-in, while the per-process risk needs Google to withdraw a key because it leaked and someone to forge tokens with it before the next refetch. Render's free tier puts the service to sleep after 15 minutes without traffic, and waking it boots the app again, the minute ADR-0005 cites, with an empty cache. Accepted for this app.
- **The start rule.** `may_start` (`src/receipts/auth/limits.py`) is pure. Signed in: no passcode, allowed while that user's runs today are under `RUNS_PER_USER_PER_DAY`. Signed out: the passcode must match (constant time), and all runs with no user today must be under `SIGNED_OUT_RUNS_PER_DAY`. A passcode never makes a visitor a signed-in user, and each branch reads only its own count. "Today" is the UTC calendar day; the limit resets at 00:00 UTC. A refusal names its count and limit, for example `5 of 5 runs used today (UTC); the limit resets at 00:00 UTC` or `20 of 20 signed-out runs used today (UTC); ...`. `LiveGate.start` (`src/receipts/api/wiring.py`) applies it in this order: the start rule, then the Keenable key (refused as `PermissionError("KEENABLE_API_KEY is not set")`, the name only), then the run starts on the same service the UI follows, then a signed-in user's run is claimed (`SqlRunRepo.claim_run`). Local demo mode (no passcode configured, and the three live settings `ANTHROPIC_API_KEY`, `KEENABLE_API_KEY` and `DATABASE_URL` not all set) replays the demo with no passcode, uncounted and unclaimed.
- **`runs.user_id` reaches the deployed Neon table through `create_schema`.** `Base.metadata.create_all` creates the new `users` table but never adds a column to an existing table, so on the Postgres dialect only, `create_schema` (`src/receipts/db/repo.py`) then sends `ALTER TABLE runs ADD COLUMN IF NOT EXISTS user_id VARCHAR(64) REFERENCES users(id)` and `CREATE INDEX IF NOT EXISTS ix_runs_user_id ON runs (user_id)`. Both are additive and idempotent. On Render they run on the first live request after the deploy (`create_schema` runs once per process, on first real use); the `ALTER` takes a brief exclusive lock on `runs`, and a nullable column with no default is a catalogue-only change on Postgres. SQLite gets the column from `create_all` on a fresh file and is not sent the DDL. The column is already on the deployed Neon database: the `db` task's integration run (`tests/test_db_constraints.py`) applied it on 2026-11-16, under the owner's answer (a) in the issue #41 plan (additive changes only, test rows deleted). Without the `ALTER`, a Postgres `runs` table created before issue #41 failed 3 of the 12 tests in that file (2 `UndefinedColumn`, 1 column assertion; the `db` judge on a throwaway local PostgreSQL 15, 2026-11-16). The DDL restates the mapping's `VARCHAR(64)`, `REFERENCES users(id)` and index name by hand; `test_create_schema_twice_is_idempotent_on_neon` checks the foreign key's target and the index name, not the column's type or length.
- **Stored data.** For a person who signs in, the `users` table stores our id (`user-` and 32 hex digits, never derived from Google's data), Google's subject id (`sub`, UNIQUE: one row per Google account), the email address and the row's creation time; nothing else from the profile (no name, no picture). `IdTokenClaims` ignores every other claim, `email_verified` included: it is not checked, so an address Google has not verified would be stored and shown. Identity is keyed on `sub`, so this affects only the stored email. The email is written at the first sign-in and not refreshed later. A person's runs carry their `user_id`; signed-out runs have `user_id` NULL.

## Consequences

- **More packages.** The lock grows from 159 to 163 packages (`grep -c '^\[\[package\]\]' uv.lock`, at `6e59412` and after `uv add joserfc`): joserfc, cryptography, cffi and pycparser (`git diff 6e59412 -- uv.lock | grep '^+name = '`). No package already in the lock changes version (`git diff 6e59412 -- uv.lock | grep '^-version'` prints nothing). `uv lock --check` exits 0. `uv run pip-audit --strict --vulnerability-service osv`, the command in `.github/workflows/security.yml`, printed `No known vulnerabilities found` and exited 0 on the new lock (run 2026-11-16 01:25–01:26 UTC, 2026-11-15 in Miami), and again on the integration head `3253fe2`, whose `uv.lock` and `pyproject.toml` are unchanged since then (run 2026-11-16 06:27 UTC). No `--ignore-vuln` was added (`grep -c ignore-vuln .github/workflows/security.yml` prints `0`).
- **Recent releases.** joserfc 1.8.0 reached PyPI on 2026-11-03, 13 days before it was locked, and cryptography sits on the sign-in path. The audit covers known advisories only, so an upgrade of joserfc or cryptography re-runs it before it merges.
- **New stored data, recorded where it stands.** AGENTS.md section 9 (Data), the spec's non-goals and "Public URL safety", ADR-0004 (a Google sign-in row and the Neon row), ADR-0005 (sign-in on the app's own domain) and the threat model change in the same PR. Deletion: a person asks the repository owner; the owner deletes the runs whose `user_id` is that person's id, then the `users` row. The foreign key has no `ON DELETE`, so Postgres refuses to delete a `users` row that runs still cite (`docs/runbooks/render.md` has the statements).
- **The API.** `POST /api/runs` keeps `X-Demo-Passcode` and is always a signed-out run, never claimed, even when the request carries a session cookie. It checks the passcode (401), then the signed-out cap (429, the detail is the start rule's reason), then the key (503). `GET /api/runs` lists the session's user's runs when the request carries a valid session cookie, else the runs with no user. `GET /api/runs/{run_id}` is unchanged: anyone with the id can read the card. The voice agent and `scripts/seed_demo_runs.py` call the list without a cookie, so they see only runs with no user, and every seeded run counts against the signed-out cap.
- **Counting, then starting, is not atomic.** `LiveGate.start` and `POST /api/runs` count today's runs, decide, and then start, with no lock or transaction across the steps. Starts sent at the same moment can each read the same count before any of them writes its row, so a person can pass their limit, and signed-out starts can pass the signed-out cap, by as many starts as arrive together. The caps bound starts made one after another, not a simultaneous burst. Accepted for a hackathon app, as the brief accepted it.
- **A just-started run belongs to no user for a moment.** `InProcessRunService.start` writes the run's row (`user_id` NULL) before it returns the id, and `LiveGate.start` claims it right after. Until that write lands, the run is listed in signed-out History and counted against the signed-out cap, and the person's own count does not include it. If the claim fails (a database error after the run started), the run keeps going, stays unclaimed, and the error reaches the UI. The window is one database write (`claim_run`); it has not been measured.
- **A deleted user's cookie.** `identify` reads only the cookie. `LiveGate.start` and `LiveGate.account` read the `users` row and treat a session whose row is gone as signed out (passcode and signed-out cap; the run is never claimed), and `/auth/me` answers 401 for it. History (`LiveGate.history`) and `GET /api/runs` still list under the cookie's stale id. In practice that list is empty: the deletion order above removes the runs before the row, and our ids are random (`uuid4`).
- **Half-configured deploys.** With all four sign-in settings set but `ANTHROPIC_API_KEY` or `KEENABLE_API_KEY` missing, there is no live repo: `/auth/login` still answers 302 and `/auth/me` 200 for a valid session, while the UI hides the sign-in link, its account line reads `0 of 20 signed-out runs used today (UTC)` (with the default cap), and the Gate treats every session as signed out: with the passcode, a run replays the demo, uncounted, or is refused for a missing `KEENABLE_API_KEY`. This fails closed.
- **Who can see an email.** `GET /auth/me` and the UI's named Gradio endpoint `POST /ui/gradio_api/run/account` both return the signed-in email to whoever holds the session cookie, and nothing about anyone else. The cookie is `HttpOnly`, so page scripts cannot read it.
- **Sessions are stateless.** Logout clears the browser's copy only; a copy taken earlier stays valid until its 7-day expiry. Changing `SESSION_SECRET` ends every session and every sign-in in progress.
- **Two algorithm pins cannot be shown by removing them on joserfc 1.8.0.** Deleting the HS256 pin in `session.py` leaves `tests/test_auth_session.py` green, because joserfc's default registry already allows only HS256, RS256 and ES256 and an HMAC key verifies only HS256; deleting the RS256 pin in `provider.py` leaves `tests/test_auth_provider.py` green, because the key set holds only RSA keys. Widening either list goes red: `tests/test_auth_session.py::test_a_garbage_session_verifies_to_none[hs512-our-secret]` for HS512, and `tests/test_auth_provider.py::test_only_rs256_is_accepted_even_from_a_key_set_without_alg` for an RS512 token (the `oidc` and `provider` judges' sabotage runs). The pins stay, in case a later joserfc changes its defaults.
- **Secrets in the code (the brief's Verification 3, as practised).** `get_secret_value()` is called to sign or verify a cookie (`session.py`), in the token request's body (`provider.py`), to build the Keenable clients (`wiring.py`), and in checks that return only a bool: the blank checks (`_is_set` in `auth/routes.py` and `api/wiring.py`) and the constant-time passcode comparisons (`check_passcode` in `api/routes.py`, `_passcode_ok` in `api/wiring.py`). None reaches a log line, an `HTTPException` detail or a response.
- **No new gate exceptions.** Pyright stays strict on `src/receipts/auth/`, and no `--ignore-vuln` flag is added.

## Alternatives considered

- **Standard library only.** HMAC covers an HS256 cookie, but nothing in the standard library verifies Google's RS256 signature, so the ID token check would need a cryptography package anyway. Rejected.
- **`authlib` (the brief's default).** It would cover JOSE and the OAuth 2.0 and OpenID Connect client helpers in one install, but measured on 1.9.6 (2026-11-16): the wheel has no `py.typed` (0 such files in either copy of the 1.9.6 wheel in the local uv cache), and a strict pyright probe outside the repository reports `create_s256_code_challenge` as partially unknown (`reportUnknownVariableType`) while the `joserfc` lines in the same probe report nothing; `import authlib.jose` prints `AuthlibDeprecationWarning: authlib.jose module is deprecated, please use joserfc instead. It will be compatible before version 2.0.0.`; and its JOSE support is joserfc, which it requires (`joserfc>=1.6.8`). The OAuth helpers it adds (the PKCE challenge, the authorization URL, an httpx client) are a few lines of standard library and httpx, and it would put one more package in the lock (164 rather than 163). Rejected.
- **PyJWT.** It also covers JSON Web Tokens and RS256 through `cryptography`. It was not measured against this lock or strict pyright; joserfc was, and it reads a JWK Set directly (`joserfc.jwk.KeySet.import_key_set`). Not chosen.
- **Gradio's `auth_dependency` on the `/ui` mount.** In the locked gradio 6.32.0 a mount with `auth_dependency` answers 401 whenever the dependency returns `None`, which would turn every signed-out visitor away from `/ui`, the opposite of option (b) (the brief for #41 records the probe). Rejected.
- **A provider built per request.** One more GET to Google's key set per sign-in, and no withdrawn key kept past the sign-in that fetched it. Not chosen; the per-process choice and its risk are under Decision.
- **Making `History` follow the row check too.** `LiveGate.history` and `GET /api/runs` could treat a session whose `users` row is gone as signed out, as `start` and `account` do. Not done in this PR: the stale id lists 0 rows once the runs are deleted first (Consequences, "A deleted user's cookie").
