# Threat model (STRIDE-light)

| Asset | Threat | Control | Test that proves the control |
| --- | --- | --- | --- |
| Secrets in the repo (API keys, tokens, credentials) | A secret is committed and reaches a fork, a log, or a public remote | Gitleaks (`.gitleaks.toml`, `.pre-commit-config.yaml`) scanning staged files and CI | `bin/red-test` plants a known-format secret and confirms gitleaks exits non-zero on it |
| Client data in the repo (names, invoice numbers, account identifiers) | Real client data lands in a tracked file via a commit, a doc, or a fixture | The leak-gate denylist (`scripts/leak_gate/`), repo-wide, no path filter | `bin/red-test` plants a denylisted pattern in a tracked file and confirms `check_tracked.py` exits 1 and names the hit |
| Third-party dependencies | A dependency ships a known vulnerability | Dependency audit job blocking merge (Dependabot alerts + `pip-audit` / `npm audit` in CI) | CI run against a pinned vulnerable version confirms the audit job fails the build |
| Run budget on the public URL (Anthropic and Keenable spend; issue #41, ADR-0008) | A passcode leaked on social media lets strangers start runs without end | Signed-out runs (the UI with the passcode, and every `POST /api/runs`) share one cap per UTC day, `SIGNED_OUT_RUNS_PER_DAY` (default 20), checked after the passcode and before the Keenable key. A signed-in person has their own limit, `RUNS_PER_USER_PER_DAY` (default 5), and never counts against the cap (`may_start`, `src/receipts/auth/limits.py`). Limit of the control: counting, then starting, is not atomic, so starts sent at the same moment can each pass at the same count (ADR-0008) | `tests/test_auth_limits.py::test_may_start` (`[signed-out-20-of-20]`, `[signed-in-5-of-5]`, `[signed-in-ignores-full-signed-out-cap]`); `tests/test_api_runs.py::test_post_run_at_the_signed_out_cap_is_429_naming_the_count`; `tests/test_wiring.py::test_signed_out_with_the_right_passcode_at_the_cap_is_refused` |
| The session cookie (who is signed in) | A forged or tampered cookie, or one signed with another key, signs a visitor in as someone else | The cookie is a compact JWT signed with HS256 under `SESSION_SECRET`, the algorithm pinned, carrying only `{uid, exp}`. Any change, another secret, or an expiry at or before now verifies to signed out (`src/receipts/auth/session.py`). Flags `HttpOnly; Secure; SameSite=Lax; Path=/`. Limit of the control: sessions are stateless, so a copied cookie works until its 7-day expiry; changing `SESSION_SECRET` ends every session | `tests/test_auth_session.py`: `test_a_session_with_one_changed_character_verifies_to_none`, `test_a_session_signed_with_another_secret_verifies_to_none`, `test_an_expired_session_verifies_to_none`, `test_a_garbage_session_verifies_to_none` (with `[alg-none-unsigned]` and `[hs512-our-secret]`); `tests/test_auth_routes.py::test_me_is_401_with_a_tampered_cookie` |
| Google's ID token (who the person is) | A forged ID token, one Google issued to another app (wrong audience), an expired one, or one replayed from another sign-in, signs a visitor in as someone else | The provider verifies the RS256 signature against Google's published keys (JWKS) with joserfc, the algorithm pinned and only RSA keys used (`src/receipts/auth/provider.py`). Then `validate_claims` checks the issuer, the audience (our client id), `exp` after now, and the nonce of this sign-in attempt (`src/receipts/auth/oidc.py`). Limit of the control: the key cache keeps a key Google has withdrawn until a token with an unknown `kid` forces a refetch or the process restarts (ADR-0008) | `tests/test_auth_provider.py::test_an_id_token_that_fails_verification_is_refused` (among its cases `[signed-by-another-key]`, `[payload-tampered]`, `[alg-none]`, `[hs256-shared-secret]`); `tests/test_auth_oidc.py`: `test_a_wrong_issuer_fails_the_iss_check`, `test_a_wrong_audience_fails_the_aud_check`, `test_an_expired_token_fails_the_exp_check`, `test_a_mismatched_nonce_fails_the_nonce_check`; `tests/test_auth_routes.py::test_claims_that_fail_validation_set_no_session_and_write_no_row` |
| The OAuth round trip | Cross-site request forgery on the callback, including login CSRF (an attacker's authorization code sent to a victim's browser signs the victim in as the attacker), or an intercepted authorization code | `state` must equal the value in a signed, host-only round-trip cookie that lasts 10 minutes (constant-time compare; present is not enough). PKCE (S256) binds the code to a verifier only the server holds, and the exchange also needs the client secret. Scopes `openid email` only. `POST /auth/logout` takes no CSRF token: a forged logout can only sign someone out | `tests/test_auth_routes.py`: `test_a_callback_with_a_wrong_state_is_400_and_sets_no_session`, `test_a_callback_with_a_state_that_only_shares_a_prefix_is_400`, `test_a_callback_without_a_valid_round_trip_cookie_is_400_and_sets_no_cookie`, `test_login_redirects_to_google_with_state_nonce_pkce_and_the_local_callback`; `tests/test_auth_provider.py::test_the_token_request_posts_the_code_verifier_and_client_credentials`; `tests/test_auth_oidc.py::test_code_challenge_matches_the_rfc_7636_appendix_b_vector` |
| Personal data of people who sign in (email, Google `sub`) | An email or `sub` reaches a log line, an error detail or a response | Only `sub` and `email` are stored. A refusal names the failed check, never a value. A database error on the `users` row during the callback is answered 503 `sign-in check failed: user_store` and dropped unread, because SQLAlchemy's error text carries both values. `GET /auth/me` and the UI's `POST /ui/gradio_api/run/account` show the email only to whoever holds that session's cookie. Limit of the control: the engine is built without `hide_parameters`, so a database error elsewhere, such as in `/auth/me`, is a 500 whose text carries our internal user id (the `routes-dbfail` judge) | `tests/test_auth_routes.py::test_a_user_store_failure_is_503_clears_the_round_trip_and_leaks_no_identity` (checks the response, the log and stdout/stderr); `tests/test_auth_routes.py::test_a_refusal_never_echoes_the_email_the_code_or_a_cookie`; `tests/test_auth_session.py::test_the_session_payload_carries_only_the_user_id_and_expiry` |
| Another person's History | One visitor's History lists another person's runs | `history_for` (`src/receipts/api/wiring.py`) lists `runs.user_id` equal to the session's user, or, signed out, the runs with no user; the UI and `GET /api/runs` both use it. By design a battlecard stays readable by anyone with its id (`GET /api/runs/{run_id}`) | `tests/test_db_users.py::test_list_runs_for_is_newest_first_and_only_that_user`; `tests/test_api_runs.py`: `test_get_runs_with_a_session_cookie_lists_only_that_users_runs`, `test_get_runs_without_a_valid_session_lists_only_runs_with_no_user`; `tests/test_wiring.py::test_history_is_the_users_runs_signed_in_and_unowned_runs_signed_out` |
| Limits after the owner deletes a person | A deleted person's still-valid cookie (it lasts 7 days) keeps passcode-free runs with no cap | `LiveGate.start` and `LiveGate.account` read the `users` row; a missing row means signed out: passcode and signed-out cap, and the run is never claimed. `/auth/me` answers 401. Limit of the control: History still lists under the stale id, which is empty once the runs are deleted before the row (ADR-0008) | `tests/test_wiring.py`: `test_a_session_whose_user_row_is_gone_is_signed_out_and_needs_the_passcode`, `test_a_session_whose_user_row_is_gone_starts_an_unclaimed_signed_out_run`, `test_a_session_whose_user_row_is_gone_meets_the_signed_out_cap`, `test_account_of_a_deleted_user_reads_as_signed_out`; `tests/test_auth_routes.py::test_me_is_401_for_a_session_whose_user_does_not_exist` |

Add rows here as new assets or controls are introduced. Every row needs a test that proves the
control fails when it should — a control without a red case is not verified.
